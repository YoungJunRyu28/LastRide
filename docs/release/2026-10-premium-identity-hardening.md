# Paid group creation — bound RevenueCat identity (2026-10-17)

**Status: source implemented and unit-tested; not yet approved for TestFlight or store release.**

## Threat being closed

Previously `POST /api/groups` accepted any caller-supplied
`X-RevenueCat-App-User-Id` and checked whether RevenueCat showed `premium` for
that ID. This is a subscription lookup, **not proof** that the HTTP caller
owns the account. Anyone who learned an active customer's anonymous RevenueCat
ID could impersonate them and create paid groups.

## Protocol v1

- Native app generates a cryptographically random **256-bit** secret using
  Expo Crypto on first use. It is saved using `expo-secure-store` in the
  Keychain / Android Keystore. The app refuses to silently replace corrupt
  secrets or fall back to AsyncStorage on an unsupported device.
- The permanent RevenueCat App User ID is **`lr_` + SHA-256 UTF-8 hex digest of
  `lastride-premium-v1:` followed by the lowercase hexadecimal secret**.
  This ID reveals no usable information about its secret.
- **First upgrade only:** `Purchases.configure` initially omits the custom ID,
  preserving the SDK's previously cached anonymous customer identity. The
  app reads its existing entitlement, then calls `Purchases.logIn(newBoundId)`
  and verifies the new CustomerInfo. This is the supported RevenueCat migration
  path: https://www.revenuecat.com/docs/customers/identifying-customers .
  Some alias configurations still do **not** merge, so successful login alone
  is never counted as confirmed entitlement continuity.
- The app persists a Keychain migration receipt: `pending-entitled` before
  switching a previously paying customer, `restore-required` if their premium
  entitlement disappears, and `complete` only after validation. On restart it
  can recover an interrupted login without losing the fact that the previous
  customer was paid. After migration, the SDK is configured directly with the
  stable bound ID before any purchase, restore or offering lookup. A failed
  offerings request cannot revoke an independently verified purchase.
- If a previously paid customer loses entitlement during migration, the paywall
  prominently explains Restore Purchases and disables a new purchase until a
  completed store restore check. Failed network/Keychain checks are **not**
  incorrectly described as an empty receipt. Successful restore clears the
  migration warning; unresolved receipts remain stored securely. A verified
  purchase/restore also refreshes the in-memory SDK migration cache, so a
  provider remount does not revive an old warning. On a later app restart,
  a stale `restore-required` marker is rechecked against real `CustomerInfo`
  before prompting again. Keychain write errors after a genuinely successful
  purchase must never be shown as a failed payment.
- Only `POST /api/groups` and lost-response creation retries submit
  `X-Premium-Device-Secret` along with `X-RevenueCat-App-User-Id`. The server
  hashes the secret and compares it in constant time before looking up
  RevenueCat and before recovery of any previously committed create key.
  Subscription expiry is **still** enforced server-side; a valid secret alone
  never grants hosting.
- The server logs neither header value, and the secret is not in a URL,
  persistent database row, or analytics. All production API requests **must**
  use TLS; proxy/WAF access logging must likewise mask the header.
- The backend requires this proof when deployed to production (including
  Lambda environments with no `NODE_ENV`). Explicit test/development and
  `LASTRIDE_STAGE=staging` retain legacy test behavior.
- The RevenueCat entitlement helper **also fails closed without
  `REVENUECAT_SECRET_KEY`** in production, including when AWS Lambda omits
  `NODE_ENV`; it must not mistake a production runtime for local development.
  The only uncredentialed exceptions are explicit test/development or staging.

## Mandatory rollout order and compatibilities

1. **DO NOT merge/deploy this patch on its own to an installed production
   population.** The existing RevenueCat anonymous IDs were generated by
   RevenueCat and are not derivable from the new secret. The app now performs
   an explicit first-upgrade anonymous-to-identified `logIn` and validates
   continuity; a successful login can still fail to alias a previously paid
   subscriber. The paywall then requires a user-initiated **Restore Purchases**
   attempt before a new purchase. RevenueCat's transfer/alias outcome depends
   on the project's restore behavior and prior alias graph; test real sandbox
   receipts and customer identity cases before rollout.
2. On staging, confirm the new RevenueCat App User ID appears in the correct
   Apple/Google/Samsung project; purchase, paywall, cancellation, expiry,
   refund and restore are scoped to the same new identity. Verify that a
   different customer can **not** pass group-create with only a stolen ID.
3. Coordinate backend-first rollout with updated iOS/Android binaries. Old
   installed clients cannot supply the capability; their group-host creation
   will receive HTTP 401 after production enforcement is enabled. **Do not
   block old clients until they can be upgraded and their purchase state
   recovered.** Add minimum-compatible-client enforcement or a documented
   migration window first. Existing groups' member tokens are unchanged.
4. Use native TestFlight devices to verify Keychain persistence across
   termination/restart, backup/restore and app reinstall. Android and iOS
   secure storage may follow different restoration rules; never promise
   cross-device purchase restoration without a user account or verified store
   receipt transfer. `expo-secure-store` Android backups must exclude
   non-restorable Keystore ciphertext.
5. Restore errors, billing API outages and SecureStore unavailability must
   show actionable user-facing guidance instead of silently enabling premium.
   Keep the existing `Restore Purchases` action prominent during the migration.
6. The device secret is a bearer capability. Its holder can operate the
   RevenueCat-linked group feature for that identity. This is **not** a
   full account-authentication, credential-recovery or cross-platform purchase
   portability solution. For future account-based access, use verified
   Sign in with Apple / other sign-in plus account-bound purchase identities.

## Production old-client rollout safety gate (2026-10-18)

**No insecure legacy-ID whitelist or fallback:** the production API refuses
caller-supplied RevenueCat IDs without proof. A client without
`X-Premium-Device-Secret` gets HTTP **403** with stable code
`PREMIUM_CLIENT_UPGRADE_REQUIRED`; a caller with an invalid proof gets HTTP
**401** with `INVALID_PREMIUM_DEVICE_PROOF`. Existing group join/member tokens
are unchanged. A client that understands the 403 error code explains that an app update is
required rather than showing a generic payment error. App versions that
predate the protocol cannot magically gain this UX until updated, so
upgrade notifications, minimum supported versions and store rollout monitoring
must be handled separately.

The deployment script invokes `node scripts/check-premium-rollout.mjs` before
reading the AWS secret, touching the production database or calling SAM.
Production requires ALL of these *manual release attestations* in addition to
existing `--confirm`, merged `origin/main`, clean git tree, licensed fresh
transit snapshot, validated secrets, staging tests and canary alarms:

```bash
# Do NOT set these values until their requirements have actually been verified:
export LASTRIDE_PREMIUM_SANDBOX_QA_APPROVED=yes
export LASTRIDE_LEGACY_CLIENT_COMPATIBILITY_APPROVED=yes
# After every merge/review of an updated production main, approve THAT sha:
export LASTRIDE_PREMIUM_ROLLOUT_APPROVED_SHA="$(git rev-parse HEAD)"
./infra/deploy.sh production "$LASTRIDE_SECRET_ID" --confirm
```

The SHA pin becomes invalid if subsequent changes produce a new commit.
`staging` requires no production approval and remains usable for testing.
These environment variables **are attestations, not automated evidence**:
they must be backed by a documented RevenueCat receipt migration matrix,
verified real sandbox purchases, old-version adoption and a rollback/launch
plan approved by the responsible release owner. Do not supply them simply to
bypass the gate. `scripts/check-premium-rollout.test.mjs` runs in CI and checks
that omitted/incorrect approvals, stale SHAs and dirty worktrees are rejected.

## Verification

- `artifacts/api-server/tests/premiumDeviceIdentity.test.ts` covers copied
  customer IDs, wrong/invalid/uppercase secrets, constant-time ID proof,
  production with missing `NODE_ENV`, and staging/test exceptions.
- `artifacts/api-server/tests/groups.test.ts` adds HTTP-level adversarial
  tests against **real PostgreSQL** for stolen customer IDs, valid active
  subscriber proof, and idempotency-key replays without owner proof.
- `artifacts/last-ride/tests/premiumDeviceIdentity.test.ts` checks
  simultaneous callers share one device secret, restart persistence, digest,
  Keychain migration receipt continuity/corruption, secure-storage loss and
  atomic storage failure. `tests/revenueCatMigration.test.ts` exercises
  first-time anonymous login, paid merge success/failure, prior identified
  customers, crash between receipt validation and login, Keychain write errors,
  SDK identity verification and restart restore state.
- Remaining steps: full CI with disposable PostgreSQL, real RevenueCat
  sandbox purchase/restore, paid TestFlight, Android store QA and approved
  migration plan. Nothing here has been applied to the production service.

## Signed-device migration acceptance matrix — not yet completed

- Upgrade an existing paid RevenueCat **anonymous** iOS customer while the app
  is online: preserve the real `premium` entitlement and allow group creation
  with the new cryptographic proof. Confirm RevenueCat dashboard alias graph.
- Repeat on Android Google Play and (if supported) Samsung Galaxy Store, each
  with the exact project API key and store billing adapter.
- Upgrade a customer whose identified target ID already has an anonymous
  alias: the ID may **not** merge on `logIn` even if `created` reports success.
  Confirm the explicit restore prompt appears and test it under each RevenueCat
  project's restore behavior. Never silently transfer someone else's receipt.
- Power-kill directly before `logIn`, during `logIn`, and after it resolves but
  before the Keychain completion receipt. Relaunch and confirm the previously
  paid marker persists without creating a second RevenueCat customer.
- Force failed `restorePurchases` (network failure, wrong store account,
  Apple ID sign-in cancelled), then confirm the UI does not claim "Nothing to
  restore" or unlock an immediate duplicate purchase on a failed check.
- Reinstall the same iOS app and sign in with the same Apple ID; repeat after
  upgrading an OS version, changing the physical phone, and switching store
  accounts. Cross-device recovery **still requires** an account-binding design
  or tested purchase restoration, and should not be promised by this patch.
- Deploy staging API first, then signed sandbox clients, then only after
  old-client compatibility and staged rollback have been approved deploy the
  enforcement. Legacy production app versions cannot create new paid groups
  after the server begins requiring the device capability.
